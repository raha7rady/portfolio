در پروژه SuperMarket (یک فروشگاه اینترنتی با ASP.NET Core MVC و EF Core)، ساده‌ترین راه برای کم‌کردن موجودی یک محصول در Checkout این است: محصول را از دیتابیس بخوان، مقدار `StockQuantity` را در حافظه کم کن، و دوباره ذخیره کن. این روش تا وقتی که فقط یک کاربر خرید می‌کند مشکلی ندارد؛ اما وقتی دو کاربر هم‌زمان آخرین واحد باقی‌مانده یک محصول را در سبد خرید خود دارند، هر دو می‌توانند Checkout را با موفقیت کامل کنند و موجودی منفی شود.

## چرا Read-Then-Write کافی نیست

مشکل اصلی این است که بین لحظه خواندن موجودی و لحظه نوشتن مقدار جدید، یک Race Condition وجود دارد؛ دو Request می‌توانند هم‌زمان همان مقدار اولیه را بخوانند، هرکدام به‌صورت جداگانه یک واحد کم کنند، و هر دو مقدار نادرستی را ذخیره کنند — بدون این‌که EF Core یا دیتابیس به‌طور پیش‌فرض متوجه این تداخل شود.

## راه‌حل: کاهش اتمیک با ExecuteUpdateAsync

به‌جای خواندن مقدار و محاسبه در حافظه، کاهش موجودی مستقیماً به‌صورت یک عبارت اتمیک در سطح دیتابیس انجام می‌شود:

```csharp
var affectedRows = await dbContext.Products
    .Where(p => p.Id == productId && p.StockQuantity >= quantity)
    .ExecuteUpdateAsync(setters => setters
        .SetProperty(p => p.StockQuantity, p => p.StockQuantity - quantity));

if (affectedRows == 0)
{
    // یعنی یا محصول وجود ندارد، یا موجودی کافی برای این تعداد باقی نمانده
    return CheckoutResult.InsufficientStock(productId);
}
```

نکته کلیدی همین شرط `StockQuantity >= quantity` داخل `Where` است: کاهش موجودی و بررسی کافی‌بودن آن، هر دو در یک عبارت SQL واحد و اتمیک انجام می‌شوند — نه در دو مرحله جدا که بین‌شان جای Race Condition باشد.

## UPDLOCK برای جلوگیری از خواندن هم‌زمان ناسازگار

در بخش‌هایی از فرآیند Checkout که لازم بود ابتدا وضعیت رکورد محصول به‌صورت قطعی خوانده شود (پیش از تصمیم‌گیری نهایی روی سفارش)، از `UPDLOCK` در سطح Query برای قفل‌کردن رکورد در طول تراکنش استفاده شد تا درخواست‌های هم‌زمان دیگر تا پایان تراکنش جاری منتظر بمانند، به‌جای این‌که مقدار قدیمی و ناسازگار را بخوانند.

## نتیجه

نه `ExecuteUpdateAsync` و نه `UPDLOCK` هیچ‌کدام راه‌حل «همیشه درست» نیستند — انتخاب بین آن‌ها به این بستگی دارد که آیا فقط یک به‌روزرسانی ساده کافی است (مثل کاهش موجودی) یا نیاز به یک تراکنش چندمرحله‌ای با قفل صریح روی رکورد داریم (مثل Checkout کامل شامل ایجاد Order و به‌روزرسانی چند محصول هم‌زمان). نکته‌ای که از این تجربه یاد گرفتم این بود: مشکلات هم‌زمانی معمولاً در تست دستی معمولی خودشان را نشان نمی‌دهند — فقط زیر بار هم‌زمان واقعی یا با تست‌های عمدی Race Condition قابل کشف‌اند.
