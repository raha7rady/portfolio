قبل از StudentInsights، Clean Architecture را فقط از روی دیاگرام‌های معروف (آن دایره‌های تودرتو) می‌شناختم. بعد از پیاده‌سازی واقعی‌اش در یک پروژه تیمی، چند نکته یاد گرفتم که در هیچ دیاگرامی نبود.

## لایه‌بندی که واقعاً استفاده کردیم

```
Domain          → موجودیت‌ها و قواعد کسب‌وکار، بدون هیچ وابستگی بیرونی
Application     → Use Caseها (CQRS + MediatR)، بدون وابستگی به EF Core یا ASP.NET
Infrastructure  → پیاده‌سازی دسترسی به داده، سرویس‌های خارجی
WebApi          → کنترلرها، تنظیمات، Middleware
```

قانون طلایی: هر لایه فقط می‌تواند به لایه‌های داخلی‌تر از خودش وابسته باشد. Domain به هیچ‌چیز وابسته نیست؛ Application فقط به Domain وابسته است؛ Infrastructure به Application و Domain وابسته است.

## جایی که گیر کردیم

بزرگ‌ترین چالش، وسوسه‌ی "میان‌بر زدن" بود. مثلاً وقتی می‌خواستیم یک Query ساده بنویسیم، وسوسه این بود که مستقیم از Controller به DbContext وصل شویم — سریع‌تر بود، ولی مرز لایه‌ها را می‌شکست.

راه‌حلی که به آن پایبند ماندیم: حتی ساده‌ترین Query هم باید از مسیر `Controller → MediatR → Handler → IApplicationDbContext` رد شود، نه مستقیم از Controller. در کوتاه‌مدت کندتر بود، ولی باعث شد منطق Application همیشه همان مسیر واحد را طی کند و مرز لایه‌ها حفظ شود.

## چرا Repository Pattern نه، بلکه IApplicationDbContext

یک تصمیم آگاهانه در این پروژه این بود که به‌جای پیاده‌سازی Repository Pattern برای هر Entity، لایه Application فقط از طریق یک انتزاع به نام `IApplicationDbContext` با Persistence کار کند. این انتزاع همان قابلیت‌های DbContext (مثل `DbSet`های موردنیاز) را در قالب یک Interface در دسترس Handlerها می‌گذارد، بدون این‌که Handlerها مستقیماً به EF Core یا Infrastructure وابسته شوند.

```csharp
// در لایه Application — فقط قرارداد
public interface IApplicationDbContext
{
    DbSet<Course> Courses { get; }
    Task<int> SaveChangesAsync(CancellationToken cancellationToken);
}

// در لایه Infrastructure — پیاده‌سازی واقعی با EF Core
public sealed class AppDbContext : DbContext, IApplicationDbContext
{
    public DbSet<Course> Courses => Set<Course>();
    // ...
}

// در لایه Application — یک Query Handler که مستقیماً از انتزاع بالا استفاده می‌کند
public sealed class GetCourseByIdQueryHandler
    : IRequestHandler<GetCourseByIdQuery, CourseDto?>
{
    private readonly IApplicationDbContext _dbContext;

    public GetCourseByIdQueryHandler(IApplicationDbContext dbContext) => _dbContext = dbContext;

    public async Task<CourseDto?> Handle(GetCourseByIdQuery request, CancellationToken cancellationToken) =>
        await _dbContext.Courses
            .Where(c => c.Id == request.Id)
            .Select(c => new CourseDto(c.Id, c.Title))
            .FirstOrDefaultAsync(cancellationToken);
}
```

این تصمیم عمداً برخلاف الگوی رایج «یک Repository برای هر Entity» بود؛ چون در ساختار CQRS، هر Query خودش مسئول شکل‌دادن به داده‌ی موردنیاز است (با LINQ روی `IQueryable`) و یک لایه Repository اضافه بین Handler و EF Core عملاً همان قابلیت `IQueryable` را محدودتر تکرار می‌کرد.

## نتیجه

Clean Architecture برای یک پروژه کوچک احتمالاً بیش‌ازحد است — دقیقاً همان دلیلی که در بک‌اند همین سایت رزومه از یک ساختار سبک‌تر استفاده کردم. ولی برای StudentInsights که چند نفر روی ماژول‌های مختلف کار می‌کردند و قرار بود ماه‌ها توسعه پیدا کند، این مرزبندی صریح باعث شد تغییرات یک ماژول، ماژول‌های دیگر را خراب نکند.
